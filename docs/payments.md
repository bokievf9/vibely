# Оплата планов (Plus, VIP)

Каркас оплаты, не зависящий от платёжной системы. **Сейчас деньги не принимаются**:
`PAYMENTS_ENABLED = false` в `src/features/plans/pricing.ts`, цены в коде `null`, адаптеров
реальных шлюзов нет. Владелец ещё не выбрал шлюз и цены.

## Как устроено

| Часть | Где |
| --- | --- |
| Таблицы, функции, математика выдач | `supabase/migrations/20261011000100_payments.sql` (комментарий в начале) |
| Типы и интерфейс адаптера `PaymentProvider` | `src/features/payments/types.ts` |
| Реестр адаптеров, выбор режима (live / test / off) | `src/features/payments/registry.ts` |
| Тестовый шлюз | `src/features/payments/providers/test.ts`, страница `/[lang]/plans/checkout/test` |
| Единый обработчик событий | `src/features/payments/process.ts` (`processPaymentEvent`) |
| Начало оплаты | server action `startCheckout` в `src/features/payments/actions.ts` |
| Вебхук | `POST /api/payments/webhook/[provider]` (`src/app/api/payments/webhook/[provider]/route.ts`) |
| Возврат пользователя | `/[lang]/plans/return?order=<id>` (опрос статуса заказа) |
| История платежей | `/[lang]/settings/payments` |
| Админка | `/admin/plans`: итоги, цены (владелец), заказы, возвраты (admin) |

Путь оплаты:

1. Пользователь жмёт «Оформить Plus». `startCheckout` проверяет вход, верификацию, режим оплаты
   и вызывает `payment_create_order` (сумма берётся из `plan_prices` в базе, не от клиента;
   один ожидающий заказ на план переиспользуется; не больше 5 новых заказов за 10 минут).
2. Адаптер создаёт оплату в шлюзе (`createCheckout`) и возвращает URL и `providerRef`;
   `payment_attach_checkout` сохраняет их; браузер уходит на страницу шлюза.
3. Шлюз присылает вебхук. Адаптер проверяет подпись (`verifyWebhook`) и приводит событие к
   `PaymentEvent`. `processPaymentEvent` сначала **записывает** событие в `payment_events`
   (уникально по `provider + event_id`), затем применяет: `payment_mark_paid` (проверяет сумму и
   валюту, выдаёт план, идемпотентно), `payment_mark_failed`, `payment_mark_refunded`.
4. Шлюз возвращает пользователя на `/plans/return`. Эта страница **ничего не решает**: она только
   показывает статус заказа из базы и опрашивает его, пока он `pending`.

Ответы вебхука: 200, когда событие надёжно записано (обработано, повтор или окончательный отказ,
например сумма не совпала: такой заказ видно в админке); 401 при неверной подписи; 500, когда
записать не удалось или ошибка может быть временной (шлюз повторит; повторное событие обработается
снова, функции идемпотентны). Принимается только шлюз из `PAYMENT_PROVIDER`; `test` вебхуки не
принимает никогда.

## Переменные окружения

| Переменная | Где | Значение |
| --- | --- | --- |
| `PAYMENT_PROVIDER` | `shared/.env.production` | `stripe`, `billplz` или `ipay88`, когда появится адаптер. Пусто: оплата выключена. |
| `PAYMENT_TEST_MODE` | `shared/.env.production` | `true`: команда (любая роль в `admins`) может пройти весь путь тестовой оплатой на проде. По умолчанию выключено. Вне production тестовая оплата доступна команде всегда. |
| Секреты шлюза | `shared/.env.production` | см. ниже, только на сервере, никогда в `NEXT_PUBLIC_*` |

Чтобы включить оплату для всех: адаптер + `PAYMENT_PROVIDER` + активные цены в `/admin/plans` +
`PAYMENTS_ENABLED = true` в коде (отдельный PR после проверки юристом).

## Как добавить шлюз

Один файл `src/features/payments/providers/<id>.ts`, реализующий `PaymentProvider`, и одна строка в
`ADAPTERS` в `registry.ts`. Остальное (заказы, вебхук, выдача плана, возвраты, админка) уже есть.

Что должен делать адаптер:

- `createCheckout(order, ctx)`: создать оплату в шлюзе на `order.amountSen` сен в MYR (или по
  `ctx.providerPriceId`, если шлюз работает с заранее заведёнными ценами), передать
  `ctx.returnUrl` как адрес возврата и `ctx.webhookUrl` как адрес уведомлений (если шлюз берёт его
  из запроса, а не из настроек кабинета), положить `order.id` в метаданные/референс. Вернуть URL
  страницы оплаты и идентификатор оплаты шлюза (`providerRef`), по которому придёт вебхук.
- `verifyWebhook({ rawBody, headers })`: проверить подпись **по сырому телу** запроса с секретом
  из окружения (сравнение за постоянное время), при ошибке бросить `WebhookVerificationError`.
  Привести событие к `PaymentEvent`: `eventId` (id события шлюза или хеш тела, если id нет),
  `type` (`paid`, `failed`, `cancelled`, `expired`, `refunded`, иначе `ignored`), `providerRef`,
  сумма в сенах и валюта **из уведомления шлюза**, `payload` только с id, статусом и суммой.
  Никаких данных карт и банковских реквизитов.
- `refund(order)` (необязательно): полный возврат через API шлюза. Если его нет, админ
  возвращает деньги в кабинете шлюза, а кнопка «Возврат» в админке только фиксирует это.

Точные названия полей, заголовков подписи и эндпоинтов берите из официальной документации шлюза
на момент подключения; здесь они намеренно не указаны.

### Stripe (карты, FPX, GrabPay)

- Секреты: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` (подпись вебхука).
- Оплата через Checkout Session в режиме разовой оплаты (FPX и GrabPay не рекуррентные);
  `providerRef` = id сессии. Вебхук: событие успешного завершения сессии и асинхронные события
  оплаты (FPX может подтвердиться позже), события возврата.
- URL вебхука в кабинете: `https://vibelydate.com/api/payments/webhook/stripe`.

### Billplz (FPX)

- Секреты: `BILLPLZ_API_KEY`, `BILLPLZ_COLLECTION_ID`, `BILLPLZ_X_SIGNATURE_KEY`.
- Оплата = bill; `providerRef` = id bill. Уведомление о результате приходит на callback URL,
  подписано X-Signature: проверять по документации Billplz.
- URL: `https://vibelydate.com/api/payments/webhook/billplz`.

### iPay88

- Секреты: `IPAY88_MERCHANT_CODE`, `IPAY88_MERCHANT_KEY`.
- Оплата через форму-редирект с подписью; `providerRef` = наш RefNo (можно `order.id`).
  Результат приходит на BackendURL с подписью: проверять по документации iPay88 и отвечать в
  ожидаемом шлюзом формате (если формат ответа отличается от JSON, это решается в адаптере/роуте).
- URL: `https://vibelydate.com/api/payments/webhook/ipay88`.

## Решения по выдаче плана

- 1 месяц = 30 дней, 3 месяца = 90 дней, 12 месяцев = 365 дней.
- Покупка продлевает: новая выдача начинается, когда закончатся выдачи того же или более высокого
  уровня (как промокоды).
- Plus при активном VIP начинается после окончания VIP.
- VIP при активном Plus начинается сразу, а оставшееся время Plus **ставится на паузу**: выдачи
  Plus сдвигаются на длину VIP, после VIP пользователь получает свой Plus целиком.
- Возврат только полный: выдача из покупки отзывается, неиспользованное время возвращается
  выдачам, стоявшим за ней в очереди (и пауза Plus сокращается на то же время).
- Поздняя оплата (заказ уже отменён или истёк) засчитывается: деньги списаны, план выдаётся.

## Хранение

Заказы и события оплаты — финансовые записи: они **не** попадают в 90-дневную очистку и
остаются после удаления аккаунта (`user_id` становится `null`). Срок хранения должен подтвердить
бухгалтер/юрист. Данные карт не хранятся никогда.
